# corpus/forwarded.txt: the forwarding chain and PROXY protocol corpus.
#
# One entry per line: <outcome><TAB><marker><rest>
#
# <outcome> is `ok`, `partial`, or a `RejectReason` (for an `f:`/`x:` entry)
# or `ProxyError` (for a `p:` entry) variant name in PascalCase. Escapes:
# `\r`, `\n`, `\t`, `\0`, `\\`, and `\xHH`. A line starting with `#` is a
# comment; an empty line is skipped.
#
# <marker> selects the consumer and is always the first two decoded bytes:
#   - `f:` feeds <rest> to `ForwardedChain::parse_into`'s `forwarded_values`.
#   - `x:` feeds <rest> to `ForwardedChain::parse_into`'s `xff_values`.
#   - `p:` feeds <rest> to `ProxyHeader::parse`.
#
# For `f:` and `x:`, <rest> is `|`-separated field LINES of the form
# `<FieldName>: <value>`, matching how the same `#list` field may legally
# arrive on the wire as several field lines that are semantically one
# comma-joined list; each segment's value (the text after its own first
# `:`, with one leading space trimmed) is fed to the matching iterator in
# order. The ONE exception is the generator marker: <rest> may instead be
# exactly `@repeat:<token>:<count>`, which expands at test time to <token>
# repeated <count> times and is fed as the SOLE line for that marker's
# iterator. This is the only generator marker this corpus uses.
#
# For `p:`, <rest> is the raw PROXY protocol header bytes, unmodified. An
# `ok` `p:` row may carry a third tab-separated field naming the expected
# `consumed` value: the byte offset where the PROXY header ends and the
# forwarded HTTP stream begins. `corpus_proxy.rs`'s `proxy` test asserts it
# when present, so accepting the header at the wrong offset is a failure
# rather than a pass on bare acceptance.
#
# Driven by two tests, both reading this SAME file: `forwarded` (in
# crates/irontraffic-http/tests/corpus.rs) handles `f:` and `x:` and skips
# `p:`; `proxy` (in crates/irontraffic-conn/tests/corpus_proxy.rs) handles
# `p:` and skips `f:`/`x:`. Each asserts it saw at least one line of its own
# kind.
